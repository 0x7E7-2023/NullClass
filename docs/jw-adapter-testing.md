# 教务适配器测试方案

适配器是**第三方脚本**，跑在用户已登录的教务页面上。这份文档说清楚：什么能自动验、
什么验不了、验不了的部分怎么办。[移植手册](jw-adapter-porting.md) 说怎么搬，
[适配器规范](jw-adapter-spec.md) 说写什么。

---

## 1. 三层验证，各自的职责

| 层 | 验什么 | 什么时候跑 | 谁能跑 |
|---|---|---|---|
| **① CI 回归门** | `parse.js` 的转换逻辑、manifest、ES5、载荷合法性 | 每次提交 | 任何人（不用模拟器、不用账号） |
| **② fixture 比对** | 同一份输入永远给同一份输出 | 同上 | 同上 |
| **③ 真机抽验** | 真实教务系统上的取数与解析 | 移植一个新平台时、上线前 | 得有账号的人 |

**关键认识：第 ① 层只跑 `parse.js`，`extract.js` 永远不会在 CI 里执行**（它需要浏览器）。
这条决定了移植时怎么切两段 —— 见移植手册 §3 第 1 步。

---

## 2. 第 ① 层：CI 回归门到底查什么

`./gradlew :importer:test` 里的 `JwLibraryHarnessTest`，对 `jw-adapters/` 下**每个**适配器：

1. **目录与 `index.json` 一致** —— 新增适配器忘了加索引条目会红。
2. **manifest 合法、key 唯一、与目录名一致**。
3. **Rhino 实跑 `parse.js`**，拿 `fixtures/*.extracted.json` 当输入，
   与 `*.expected.json` 逐字段比对（键顺序无关、**数组顺序有关**）。
   没有 `parse.js` 时退化为「`extracted` 必须等于 `expected`」。
4. **期望载荷本身必须过校验与归一化** —— `JwPayloadCodec.decode` + `JwScheduleNormalizer.normalize`。
   周次越界、节次矛盾、缺学期名这类错误在这里就拦住。
5. **ES5 写法检查** —— 源码里不得出现 `=>`、反引号、`let `、`const `。
6. **内置资源与磁盘目录一致** —— 打包进 APK 的那份不能和仓库里的不一样。

**这一层能挡住什么**：转换逻辑写错、周次切错、字段名打错、ES6 语法混进来、载荷越界。
**挡不住什么**：`extract.js` 里的一切（选择器写错、接口路径错、请求参数错）。
所以 `extract.js` 要**尽量薄** —— 它的正确性只能靠第 ③ 层和用户反馈。

## 3. 第 ② 层：fixture 从哪来

规范要求「真实抓取」。对**移植来的**适配器我们做不到：上游 226 所学校，我们一个账号都没有。
所以移植件的 fixture 是**合成的**：按上游脚本实际读取的字段形状，编一份形状正确的原始数据。

**代价必须说清楚**：合成 fixture 只保证「同样的输入永远得到同样的输出」，
**不保证解析在真实页面上是对的**。这和内置 `universal` 适配器的 fixture 是同一个档位
（规范 §7 已经为它开过这个例外，并写明「换成真实 dump 才算数」）。

**因此**：

- 移植件的 fixture 必须在文件头注明**合成来源**，别让它看起来像真实抓取；
- 谁哪天拿到了真实 dump，**替换 fixture 并重跑门**是最高优先级的贡献；
- **正确性 bug 会以用户反馈的形式回来**（某学校少了几门课、周次错位）。这是接受的代价 ——
  审计审的是安全性（见移植手册 §5），正确性靠反馈迭代。

fixture 该放几份：至少一份「基本表格」。**值得多放一份边界**（空周次、单双周、连堂、
跨多节的课），因为这些正是上游脚本各写各的地方。

### 3.1 fixture 自证是真隐患（不是理论问题）

移植时最自然的做法是：写完 `parse.js`，跑一遍，把输出存成 `expected.json`。**这等于什么都没验** ——
它只把「当前行为」钉住了，钉住的可能是错的。CI 会愉快地绿。

这不只是理论上难看，第一批就撞上了：

> 湖北医药学院的 `parse.js` 把 `1-16周(双)` 解析成 **每周都上**（应为双周），且不报警 ——
> 「单」「双」写在「周」字后面时，标记会落到另一个分段里被丢掉。
> 而这个适配器**有 fixture、CI 是绿的**：它的用例里连「单」「双」两个字都没出现过。
> 换成 `1-16周(单)`、`双周1-16` 同样塌成每周。山西工程职业学院是同一个位置零覆盖
> （用变异测试证出来的，见下）。

两条规矩能挡住这类事：

1. **新用例的期望值要独立推出来**，按规范算该是什么，而不是把 `parse.js` 的输出贴进去当期望。
   写得出期望值，说明你知道正确结果是什么；写不出，说明这块逻辑你自己也没想清楚。
2. **证明这条用例真的能拦住错**：做一次变异测试 —— 把 `parse.js` 里对应的逻辑**故意改坏**，
   跑一遍。新用例必须变红；如果它照旧绿，那它盖的不是你以为的那条路径。

   ```
   原始              basic=MATCH  new-case=MATCH
   变异（改坏那处）   basic=MATCH  new-case=DIFF     ← 新用例真的在看着它；旧用例盖不住
   ```

**每个平台批次都要为「这个平台最容易写错的编码」单独造用例**：周次写法（`单/双` 在括号里、
在「周」后面、`隔周`、`1-3,5周` 混排）、节次写法（`01-02节` / `0102` / `第9,10节` / 连堂标签）、
分页行为（有没有总数、取不满时停不停）。这些地方各校写法不统一，也是历史上真正出过错的地方。

### 3.2 批量移植时，别信「同平台」这个标签

**平台标签不可信，包括这份文档和其它文档里给出的分类表。** 第一批 8 个里有两处标错：
马鞍山学院被标成「青果」（青果的课表常画在 canvas 上、要转 OCR），实际是**强智 eams**、
课表是真 `<table>`；衡阳师范学院走 `jsxsd` 路径、被归到「正方老版」，实际是**湖南强智**
（打开该校公开登录页就能看到厂商名）。**按脚本实际请求的接口路径 + 选择器结构聚类**，
不要按上游注释、也不要按别人给的分类表。

而且**同平台的可复用性是分层的**：

| 层 | 能不能复用 |
|---|---|
| 接口信封（路径前缀、请求头、返回结构 `{code,datas:{...:{rows:[]}}}`） | 常能 |
| 行字段名（`KCM` / `SKXQ` / `KSJC` …） | 常能 |
| **取数路径**（具体接口、要哪些参数、要不要先取学号） | **未必** |
| **周次 / 节次编码** | **未必** |
| 分页行为 | **未必** |

第一批实测：某平台三所学校里，两所是**逐字克隆**（`diff` 只有注释、主机、作息表、提示语四处差异），
第三所同接口同字段但参数与周次编码不同；另一个平台的两个部署**连接口都不一样**。

所以**同平台的第二个不要照抄第一个的 `parse.js` 就算完** —— 拿它自己的真实编码单独造用例。
批量搬时最容易出错的地方，正是「以为一样」。

## 4. 第 ③ 层：真机抽验

### 什么时候必须做

- **移植一个新平台的第一件**（摸清取数方式，确认接口路径没变）；
- **发布前**，对当次要发的适配器至少抽一个。

### 怎么做

我们有两个**已经有真机经验**的学校可以对照：`dlutci`（金智 jwapp）、`ustc`（for-std）。
同平台的移植件可以拿它们当参照，验证选择器/接口是否同构。

模拟器上跑的方法（LDPlayer / Android 14）：

1. 调试包 `adb install -r`（`com.nullclass.app.debug`，与正式版并存）；
2. 起一个本地 HTTP 服务 + `adb reverse tcp:8000 tcp:8000`，临时把测试适配器的
   `loginUrl` 指到 `http://localhost:8000/` —— 这样**不用真教务页面**也能验
   「桥注入了没、脚本跑没跑、载荷对不对」这半条链；
3. `adb exec-out screencap -p` 逐屏核对（**别用 `uiautomator dump`**：它会触发 Activity 重建、打断流程）；
4. 真机日志：`adb logcat`（tag `NullClass.Jw`）与 `files/jw-last-error.log`（`run-as` 可读）。

> 模拟器上的**数据持久化结论不可信**（雷电的 WAL 可见性有坑）：验证持久化要用
> 「force-stop → 确认进程死亡 → 重启 → 看 UI」。

### 验收标准（移植件）

| 项 | 标准 |
|---|---|
| CI 门 | 绿，且**反向对照**过（故意改坏 fixture 会红，证明它真在跑） |
| 载荷 | 归一化后能在课表里正常显示：节次不越界、周次不越界、连堂连成一块 |
| 开学日 | 有就准；没有则**推算值必须出现在导入预览的「适配器说明」里** |
| 丢数据 | 解析不了的课必须进 `warnings`，不许静默丢 |
| 安全 | 移植手册 §5 的 8 条逐条签过，写进 `AUDIT.md` |

## 5. 上游更新了我们怎么办

上游是活跃仓库。我们搬的是**某一时刻的快照**，不追上游（追不动，也没必要）。

- 适配器目录里记下**上游 commit / 日期**，便于日后比对；
- 上游修了 bug 时，**重跑移植**比打补丁干净 —— 反正转换逻辑在 `parse.js`，重搬一遍成本很低；
- **不引入自动同步**：上游没人替我们审安全性，自动拉取等于把审计外包给不认识的人。

---

## 6. 反馈回路

移植件正确性靠用户反馈迭代，所以要让反馈**便宜**：

- 提取失败时界面可复制日志（已有），包含适配器 key、URL、控制台日志；
- 适配器详情页能看**脚本全文**（已有）—— 用户或第三方可以直接指出哪一行错；
- 每个适配器的 `warnings` 是给用户的第一手线索：「开学日是推算的」「这门课只有自定义时间」。

**上线节奏**：新平台的第一件**单独发**，观察一轮再批量搬同平台的其余件。
一批里有一个坏的，比一批全是坏的好收拾。
